# Database Layer

This application uses **PostgreSQL** as its data store. The schema is
owned entirely by the backend's SQLAlchemy models and versioned via
**Alembic** migrations (`backend/migrations/`) -- there is no manual
SQL to run and no separate schema-management tool.

## Why this directory is mostly empty

Unlike the frontend and backend, the "database" tier here is a managed
PostgreSQL instance (via Docker Compose locally, or a managed/self-hosted
PostgreSQL service in production), not application code. This directory
exists to:

1. Document the schema, ownership, and permissions (see below).
2. Hold optional first-run initialization scripts in `init/` (only
   needed for things Alembic migrations don't cover, such as creating
   extensions).

## Schema overview

### Table: `tasks`

| Column        | Type                     | Constraints                                              |
|---------------|--------------------------|------------------------------------------------------------|
| `id`          | `VARCHAR(36)`            | Primary key, UUID string, generated by the application     |
| `title`       | `VARCHAR(255)`           | `NOT NULL`                                                  |
| `description` | `TEXT`                   | Nullable                                                    |
| `status`      | `VARCHAR(20)`            | `NOT NULL`, default `'pending'`, `CHECK` in `('pending', 'in_progress', 'completed')` |
| `created_at`  | `TIMESTAMP WITH TIME ZONE` | `NOT NULL`, set on insert                                 |
| `updated_at`  | `TIMESTAMP WITH TIME ZONE` | `NOT NULL`, set on insert and update                      |

Indexes:
- `pk_tasks` (primary key) on `id`
- `ix_tasks_status` on `status` (supports status filtering in the API)
- `ix_tasks_created_at` on `created_at` (supports ordering)

There are no foreign keys in the current schema (single-table
application). Future related tables (e.g. `users`, `task_tags`) should
follow the same Alembic-migration workflow.

## Database, user, and required permissions

| Item              | Value (default / local)      | Notes                                                        |
|-------------------|-------------------------------|----------------------------------------------------------------|
| Database name     | `taskdb`                      | Set via `DATABASE_NAME`                                        |
| Application user  | `taskuser`                    | Set via `DATABASE_USER`                                        |
| Required grants   | `CONNECT`, `CREATE`, `USAGE` on the `public` schema; full DML (`SELECT/INSERT/UPDATE/DELETE`) on all application tables; `CREATE`/`ALTER`/`DROP` on tables if this user also runs migrations | In stricter environments, use a separate, lower-privileged runtime user and a separate migration user with DDL rights |

In Docker Compose, the official `postgres` image creates this database
and user automatically from `POSTGRES_DB` / `POSTGRES_USER` /
`POSTGRES_PASSWORD`, each superuser-equivalent within that database.
In a managed production PostgreSQL service, DevOps/DBAs should
provision a database and a dedicated application role with the grants
above (see `docs/DEVOPS_HANDOVER.md`).

## Migrations

Migrations live in `backend/migrations/versions/` and are run with
Alembic (via Flask-Migrate). See the root `README.md` "Database Setup"
section and `docs/DEVOPS_HANDOVER.md` "Database Migration Strategy"
for exact commands and the recommended way to run them during
deployment.

## `init/`

Optional `.sql` or `.sh` scripts placed in `database/init/` are
executed once, automatically, by the official `postgres` Docker image
the **first time** its data volume is created (not on every restart).
This project does not currently require any init scripts -- schema
management is handled entirely by Alembic -- but the directory is kept
so DevOps has an documented, discoverable place to add things like
PostgreSQL extensions (e.g. `CREATE EXTENSION IF NOT EXISTS pgcrypto;`)
if a future feature needs one.
